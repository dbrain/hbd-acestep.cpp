## VRAM anatomy (the important part)
The pipeline runs **two stages, never co-resident** (`sglm_free()` before the audio stack loads),
so **peak = max(LM stage, decode stage)**. Both stages were profiled:

### LM stage (text→tokens)
- Q8 weights **5.10 GB** / Q4_K_M weights **2.86 GB** (resident on GPU).
- KV cache **F16, 2 sets (CFG cond+uncond), main 36L + sub 12L, Nh16×D128**:
  - 10s gen (S=1457): **1092.8 MB**
  - 30s gen (S=1957): **1467.8 MB**
  - KV is dominated by the ~952-token static conditioning prefix (desc 600 + audio 252 + type 100).
- Activations ~0.3 GB.
- ⇒ LM-stage peak: Q8 ≈ **6.8 GB @30s**, Q4 ≈ **4.6 GB @30s**.

### Decode stage (tokens→wav: RVQ + CFM-ODE + VAE) — **THE WALL**
- CFM weights 1.33 GB (BF16) + VAE 0.17 GB + septoken/musicfm encoders.
- **The decode is NOT chunked below 30s**: `chunk_frames = 750` (30s). At ≤30s the whole song is
  decoded in ONE VAE graph (519 nodes, T_latent=750 → 1.44 M samples) → huge activation buffers.
- ⇒ decode-stage peak at 30s = **9235 MiB**, *independent of LM quant* (basic-Q8 == basic-Q4 == 9235).
  This is the binding constraint and it grows with duration.

### The headline finding
> Neither Q8 nor Q4 fits 4 GB at 30s today, because the **un-chunked decode stage hits 9.2 GB**.
> Q8 LM weights (5.1 GB) *also* can't fit 4 GB resident. The path to ≤4 GB needs **both**:
> 1. **Chunk the CFM+VAE decode** (caps decode VRAM at any song length — algorithm already present,
>    just `chunk_frames` too high + not CLI-exposed).
> 2. **Q4_K_M (or an intermediate Q5/Q6) LM weights + KV quant/right-size** (caps the LM stage).

## Optimization plan (ordered)
1. **Decode chunking** — lower `chunk_frames`, expose as knob; measure VRAM vs chunk size + ear-check the crossfade. (VRAM, both quants)
2. **LM quant ladder** — Q4_K_M baseline; mint Q5_K_M / Q6_K from BF16 as middle ground; pick by ear + budget.
3. **KV cache**: F16→Q8_0 (≈ −0.5 GB) and/or right-size the conditioning prefix to actual lyric length.
4. **Speed**: LM decode is launch-latency bound (~300 tiny kernels/fwd at N=2/S=1, compute≈total).
   Investigate CUDA-graph capture (defeated today by per-step KV-length change) + op fusion.
5. Profile every hot kernel with ncu; prove the floor from compute + memory angles.

## Lever 1 — decode chunking (DONE, measured)
`SG_CHUNK_FRAMES` env override added to `sgpost_decode` + `sgpost_decode_continue` (was hardcoded 750).
Q4, 30s gen, peak VRAM vs chunk:

| chunk_frames | seconds/chunk | segments | peak VRAM |
|---|---|---|---|
| 750 (baseline) | 30 | 1 | 9235 MiB |
| 375 | 15 | 2 | 5481 MiB |
| **250** | 10 | 3 | **4631 MiB** |
| 150 | 6 | 4 | 4631 MiB |

At chunk ≤ 250 the decode stage falls below the LM stage → peak plateaus at **4631 MiB = the LM stage**
(Q4 weights 2.86 + KV 1.47 + act). So chunking caps the decode stage at ANY song length; 250 is the
sweet spot (largest chunk that hits the plateau, best crossfade quality). Decode-stage VRAM is now
duration-independent. Remaining wall: the LM stage (KV-dominated) → Lever 3 (KV).

## Lever 2 — flash attention on the LM decode (DONE, validated)
Switched both decode attention paths (`sggen_attn`, `sggen_attn_batch`) from the manual
QKᵀ/softmax/transpose/×V chain to `ggml_flash_attn_ext` (SGLM_NO_FA reverts). The prefill oracle
(`songgen-lelm.h`) already used FA and passes the golden gate, so FA is numerically faithful here
(>0.999 logit cossim; the original gate already compared FA-prefill vs manual-decode).
- **LM step 51 → 35 ms (−32%)**; KV-vs-prefill gate still PASS >0.999.
- **GPU SM utilization median 97%** during decode → FA already removed the launch-latency overhead;
  the decode is throughput-bound, NOT launch-bound (so CUDA-graph capture would not help).
- FA also reads K/V straight from the cache layout (un-transposed V) → enables a quantized KV cache.

## Lever 3 — Q8_0 KV cache (DONE, validated; found+fixed a latent corruption bug)
`SG_KV_TYPE=q8_0|q4_0|f16` (default f16; deploy uses q8_0). FA reads the quantized cache directly.
- **q8_0 KV: −47% (1468 → 780 MB @30s)**, gate PASS >0.999. q4_0 KV → CUDA illegal access (task #7).
- **BUG FOUND (ear-caught, "horror-movie wash"):** the single/prefill attention path hardcoded F16
  strides (`ggml_type_size(GGML_TYPE_F16)`) for the KV-cache write/read. With a Q8_0 cache the
  conditioning-prefix KV was written at F16 offsets while the batched decoder read at Q8_0 offsets
  → corrupted prefix → degenerate generation. The KV-vs-prefill gate MISSED it because there write+read
  use the same (wrong) strides → self-consistent. FIX: use the cache tensor's own `nb[]`. Isolation that
  caught it: FA+F16 = healthy song (flux 0.58); FA+Q8_0 = wash (flux 0.33, rms 0.09 ½ amplitude); after
  fix FA+Q8_0 @30s = flux 0.705, rms 0.19, healthy. LESSON: the logit gate is necessary but not
  sufficient — added a `wav_metric.py flux/flatness` regression check and ear-confirmation on every
  generation-path change (metrics alone declared a broken build "a win" once — don't repeat).

| kernel | SM% | DRAM% | role |
|---|---|---|---|
| **mul_mat_vec_q** (dominant) | ~75 | ~70 | Q4 weight matmuls (q/k/v/o proj, MLP, lm_head) |

| flash_attn_ext_f16 | 11 | 56 | FA (cheap, mem-bound on KV reads) |
The decode is dominated by `mul_mat_vec_q` at **~70–75% of BOTH compute and memory roofline** — near

(97% SM). Materially faster would require fewer/smaller weights (already Q4) or higher effective batch
(decode is fixed at N=2 for CFG). → LM decode is at its floor for this model+quant.

## Lever 4 — dynamic/growing KV + model-max EOS ceiling (task #8/#9, DONE, validated)
Upstream SongGeneration-v2-large has **no duration target**: it generates to the model max
(`config.yaml max_dur=270 s` = 6750 frames @ 25 fps) and stops on **EOS**. Pre-allocating KV to
that ceiling = ~3.2 GB (q8_0) on top of 5.1 GB Q8 weights → over every bucket, *even for a 30 s
song*. Growing KV decouples the ceiling from the footprint.

**Implementation** (`songgen-lelm-gen.h`):
- `sggen_alloc_kv_dyn(g, m, init_seq, cap_seq, n_sets)` — start at `init_seq` (prefill + delay
  headroom ≈ 1207), grow on demand up to `cap_seq` (the hard ceiling). `sggen_alloc_kv()` (clone/
  continue/test) unchanged → `init==cap`, i.e. exactly the old one-shot alloc.
- `sggen_ensure_kv()` called before every step: geometric (≈doubling) growth for ~linear total
  copy cost, but the per-grow increment is capped at `SG_KV_GROW_BLOCK` frames (default 1500 ≈ 60 s)
  so we don't over-allocate near the ceiling (bounds both overshoot and the grow transient).
- `sggen_grow_kv()` is **host-bridged**: stage the populated `[0,used)` prefix of every cache tensor
  down to host, free the old GPU buffer, build the bigger buffer, upload. Old+new buffers are never
  co-resident → grow transient = weights + max(old,new) KV (NOT old+new, which spiked the 156 s
  render to 10,013 MiB before this fix). `nb[1]` (D-row bytes) is capacity-independent so each
  (set,head) slab is one contiguous `used*nb[1]` byte run — raw move, KV-type-agnostic.
- `songgen-generate`: no `--duration`/`--frames` → `max_gen_len = SGGEN_MODEL_MAX_FRAMES` (6750, 270 s),
  EOS-terminated. `--duration` is now an explicit **hard cap** (truncate) for bounding length/VRAM.
- server `/generate`: omit `duration` → model-max EOS-natural; explicit `duration` = hard cap.

**Correctness**: dynamic (with real grows) is **bit-identical** to static — `wav_metric cmp` waveform
corr 1.0000 / log-mel RMSE 0.0000 at 30 s (1 grow) and re-confirmed after the host-bridge change. Grow
only moves bytes. Cost ≈ 0.2–0.7 s per grow (host round-trip), 3–4 grows for a 156 s song → noise on a
~300 s render.

**The win (measured over the HTTP API, server model-max default, EOS-terminated):**
| config | natural EOS | KV final buf | **peak VRAM** | RTF | 7.5 GB? |
|---|---|---|---|---|---|
| Q8 + q8_0 KV, 6-verse lyric | **156 s** | 6914 (2.67 GB→capped) | **7579 MiB** | 2.03 | ✓ fits |
| Q8 + q4_0 KV, 6-verse lyric | **175 s** | 6914 (1.46 GB) | **6887 MiB** | 2.10 | ✓ comfortably |
| Q8 + q8_0 KV, short golden, 220 s ceiling | 35 s | 961 MB (not the 2.67 GB ceiling) | 6803 MiB | — | pays for real length |
| Q8 + q8_0 KV, basic 30 s | (capped) | 779.7 MB | 6151 MiB | 2.09 | == old static |

Pre-fix (doubling, co-resident grow) the 156 s render spiked to **10,013 MiB**; host-bridge + block-cap
dropped it to **7579** (measured) → now fits 7.5 GB. So you set the ceiling to the model max and the
footprint tracks the EOS-determined real length. **Song length is lyric-driven** — the short golden prompt
EOSes ~35 s; a 6-verse lyric sustains to 156–175 s (q8_0 vs q4_0 walk different sampling paths).
Ear A/B staged on the eartest page: `dynkv-q8-q8kv-156s` vs `dynkv-q8-q4kv-175s` (+ `kv-{q8,q4}kv-30s`).

**LM step timing (Q8, N=2 CFG-batched)**: 42 ms @ short KV → 52 ms @ 1000 steps (grows with KV length;
FA reads the full cache each step). vs Q4 35 ms — Q8 is ~34% slower/step (more weight bytes; decode is
weight-load-bound per the ncu floor). Whole-pipeline 30 s: wall 62.6 s, RTF 2.09, 16 step/s.

## Lever 5 — weight offload / CPU streaming (task #8, QUANTIFIED — verdict: not for the LM)
Question: can we stream weights (sd.cpp/flux2-style) to cut the 5.1 GB Q8 LM footprint? Cost of
streaming a tensor = `size × reads_per_song / PCIe_BW`. **PCIe H2D ≈ 12 GB/s** here (measured from the
KV-grow host round-trips). The LM is **weight-load-bound at VRAM BW (~360 GB/s)** — moving a weight to
PCIe makes *that weight* ~30× slower to read.

| component | Q8 size | reads / song | stream verdict |
|---|---|---|---|
| conditioning embeds (desc/type/audio_emb) | small | **once** (prefill) | ~free to offload |
| CFM estimator + VAE | 1.33 + 0.17 GB | per ODE/decode step (few × chunks) | sd.cpp-viable, **but not the peak** (decode already chunked < LM stage) |
| **48 transformer layers + lm_head** | **~5.1 GB** | **once per AR step → 1000–4100×** | the hog *and* the most reused → worst candidate |

With prefetch overlap, the free budget = what hides under the 47 ms/step compute ≈ **~560 MB (~5 layers)**.
Beyond that ≈ **+83 ms/step per streamed GB**. Reaching 3.5 GB needs offloading ~2.6 GB → +215 ms/step →
**~5.5× slower LM** (non-viable). **Conclusion: weight streaming buys ~0.5 GB free on Q8 and nothing more
at usable speed; it cannot put Q8 into 3.5 GB.** The decode-stage weights could be streamed but aren't the
peak. The real Q8 levers are the KV (dynamic — done; q4_0 — below). Q4_K_M weights remain the only thing
under 4 GB.

## Lever 7 — weight×KV quality ladder (argmax-agreement vs a FIXED Q8 ruler)
`songgen-lelm-gen-test` now takes an optional 3rd arg `ref_gguf`: the oracle (full-prefill reference)
loads `ref_gguf` while the KV-decode path loads `gguf`. Default `ref==gguf` = self-consistency (old
behaviour). Pass a near-lossless gguf (Q8_0) as a **fixed ruler** to compare ACROSS weight quants — the
self-consistency form is KV-comparable only (the oracle moves with the weights). It also prints
per-codebook **argmax agreement** (teacher-forced, same fed tokens), the metric that actually predicts
token flips (cb1/cb2 are argmax-sampled), not just logit cosine.

64 teacher-forced steps, agreement vs **Q8_0 full-prefill**:
| weights | KV | cb0 | cb1 | cb2 |
|---|---|---|---|---|
| Q8   | f16  | 93.8% | 90.6% | 95.3% |
| Q8   | q8_0 | 95.3% | 92.2% | 84.4% |
| Q8   | q4_0 | 90.6% | 73.4% | 65.6% |
| Q4_K | f16  | 76.6% | 68.8% | 48.4% |
| Q4_K | q8_0 | 76.6% | 68.8% | 50.0% |
| Q4_K | q4_0 | 71.9% | 68.8% | 43.8% |

Reading it:
- **~90–95% is the noise floor** (`q8w f16kv` is ~the ruler yet ≠100%): decode-vs-prefill mechanism +
  argmax near-ties. ~92% = "effectively identical".
- **q8_0 KV ≈ f16 KV** (lossless); **q4_0 KV** drops cb1/cb2 ~20–30 pts → real but modest perturbation.
- **Weight quant dwarfs KV quant.** f16-KV column = pure weight effect: **Q4_K weights crater cb2 to 48%**
  vs Q8's 95% — a bigger perturbation than q4_0 KV (cb2 66%). And Q4_K_M is the **ear-approved** config.
  ⇒ argmax-agreement is a **perturbation-magnitude** metric, NOT an audibility verdict (it would reject the
  weights we already shipped). By that ground truth, **q4_0 KV is comfortably acceptable** (less perturbing
  than Q4_K weights).
- **On Q4 weights, KV quant is free** (cb1 flat 68.8%, cb2 48/50/44 = noise) — Q4_K + q4_0 KV ≈ Q4_K + q8_0
  KV. Weights are the quality knob; KV precision is second-order.

**Benchmarking/perf-tuning config locked to Q8 weights + q8_0 KV** (quality-safe, ~lossless KV).

## Deep profile (Q8 + q8_0 KV, 156 s song over HTTP) — where the cycles go
Per-line-timestamped long render (`SGLM_PROFILE=1`):
- **LM AR decode = 89% of wall (280 s), audio decode (CFM/VAE) = 11% (35 s).** The LM is the whole game;
  the decode stage (RTF 0.23) has little to give and is already chunk-bounded.
- **LM step time GROWS with KV length**: 42 ms @ step 50 → 90 ms @ step ~4100 (ragged FA read of the whole
  KV every step). This growth — not the base matmul — dominates long-song wall.

## Lever 8 — port acestep's 256-bucketed FA KV-read to the songgen LM (DONE, HUGE at long context)
The +17.6% KV-read bucketing (commit 62fc672) lived in the **acestep** LM (`qwen3-lm.h`); songgen's LM
(`songgen-lelm-gen.h`) is a separate file and **never got it** — it read a ragged `kv_len`, so the CUDA
flash-attn decode fell off its 256-aligned vec fast path at essentially every step (kv_len rarely %256==0).
Ported to `sggen_step_batch`: round the FA read up to a 256 stride (`SG_KV_BUCKET`, default 256), pad the
read with -inf mask (cache is zeroed at alloc/grow → inert tail), and `sggen_ensure_kv` covers the padded
read. Single-step/prefill path left ragged (runs once).

**Measured (Q8 + q8_0 KV), marginal ms/step:**
| step (~KV len) | ragged (before) | 256-bucketed |
|---|---|---|
| 50   | 42.3 | 31.4 |
| 1000 | 53.4 | 32.6 |
| 2000 | 65.3 | 33.9 |
| 2800 | 74.7 | ~34 |
| 3750 | ~88  | 36.2 |

The fast path is faster *and* nearly **flattens** the growth (31→36 ms across a 150 s song vs 42→90 ms).
For a 156 s song the LM term drops ~**280 s → ~145 s (≈2×)**; whole-song RTF ~2.0 → ~1.1. Validated:
gate cossim still >0.999; dynamic==static still bit-identical (both bucketed); songs healthy (0% clip).
Bucketing changes FP block-accumulation → at temp=0 greedy a borderline argmax can flip (different-but-
equivalent), same caveat as acestep; `SG_KV_BUCKET=1` reverts to ragged/bit-exact.

## Conditioning-prefix right-size — INVESTIGATED, low value (not the win it looked)
The static prefix is desc(600) + audio(252) + type(100). But the **600-token "desc" region is the LYRICS**
(`<|im_start|>"+lyric`), padded to 600 — it **scales with the song**: long lyrics (→ long songs, where KV
binds) fill it near-full, so there's little pad to trim exactly when you'd want to. Short lyrics have lots
of pad but make short songs that don't need the budget. cond/uncond must share KV length (lockstep N=2
batch), so you can't exploit the near-empty uncond desc. The only constant overhead is the 252 audio-prompt
slots (all-SP for text2music) + ~80 type pad ≈ 330 tokens (~130 MB q8_0); trimming the audio region risks
the trained conditioning layout (the model was trained with the prompt-audio region present) and PAD/SP
positions do carry embeddings into the KV (attended), so it's not a free trim. **Verdict: skip for the
long-song case; only marginally helps short songs, with a faithfulness risk. Not pursuing.**
