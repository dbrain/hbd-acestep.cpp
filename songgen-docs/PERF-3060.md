## VRAM anatomy (the important part)
The pipeline runs **two stages, never co-resident** (`sglm_free()` before the audio stack loads),
so **peak = max(LM stage, decode stage)**. Both stages were profiled:

### LM stage (text→tokens)
- Q8 weights **5.10 GB** / Q4_K_M weights **2.86 GB** (resident on GPU).
- KV cache **F16, 2 sets (CFG cond+uncond), main 36L + sub 12L, Nh16×D128**:
  - 10s gen (S=1457): **1092.8 MB**
  - 30s gen (S=1957): **1467.8 MB**
  - KV is dominated by the ~952-token static conditioning prefix (desc 600 + audio 252 + type 100).
- Activations ~0.3 GB.
- ⇒ LM-stage peak: Q8 ≈ **6.8 GB @30s**, Q4 ≈ **4.6 GB @30s**.

### Decode stage (tokens→wav: RVQ + CFM-ODE + VAE) — **THE WALL**
- CFM weights 1.33 GB (BF16) + VAE 0.17 GB + septoken/musicfm encoders.
- **The decode is NOT chunked below 30s**: `chunk_frames = 750` (30s). At ≤30s the whole song is
  decoded in ONE VAE graph (519 nodes, T_latent=750 → 1.44 M samples) → huge activation buffers.
- ⇒ decode-stage peak at 30s = **9235 MiB**, *independent of LM quant* (basic-Q8 == basic-Q4 == 9235).
  This is the binding constraint and it grows with duration.

### The headline finding
> Neither Q8 nor Q4 fits 4 GB at 30s today, because the **un-chunked decode stage hits 9.2 GB**.
> Q8 LM weights (5.1 GB) *also* can't fit 4 GB resident. The path to ≤4 GB needs **both**:
> 1. **Chunk the CFM+VAE decode** (caps decode VRAM at any song length — algorithm already present,
>    just `chunk_frames` too high + not CLI-exposed).
> 2. **Q4_K_M (or an intermediate Q5/Q6) LM weights + KV quant/right-size** (caps the LM stage).

## Optimization plan (ordered)
1. **Decode chunking** — lower `chunk_frames`, expose as knob; measure VRAM vs chunk size + ear-check the crossfade. (VRAM, both quants)
2. **LM quant ladder** — Q4_K_M baseline; mint Q5_K_M / Q6_K from BF16 as middle ground; pick by ear + budget.
3. **KV cache**: F16→Q8_0 (≈ −0.5 GB) and/or right-size the conditioning prefix to actual lyric length.
4. **Speed**: LM decode is launch-latency bound (~300 tiny kernels/fwd at N=2/S=1, compute≈total).
   Investigate CUDA-graph capture (defeated today by per-step KV-length change) + op fusion.
5. Profile every hot kernel with ncu; prove the floor from compute + memory angles.

## Notes / open items surfaced during baseline review
- **Seed consistency**: every baseline sample used seed=1234. Q8 vs Q4 still differ — quant shifts
  cb0 logits → the top_k multinomial walks a different path even on an identical RNG stream. Same-seed
  ≠ same-song across quants (documented on the ear-test page).
- **clone "ends early"**: full 375 frames (15.0s) rendered, no early EOS — musical content of the short
  clone lyric resolves before 15s. Revisit in the clone-quality pass.
- **/continue garbled (Q8 + Q4)** — TASK open. /clone uses identical server plumbing and is fine, so the
  fault is in the continuation algorithm (VAE-encode prompt → in-context true_latents → CFM), the
  least-tested path (no numeric golden, prior OOM history). Deferred until core VRAM/perf lands.

## Lever 1 — decode chunking (DONE, measured)
`SG_CHUNK_FRAMES` env override added to `sgpost_decode` + `sgpost_decode_continue` (was hardcoded 750).
Q4, 30s gen, peak VRAM vs chunk:

| chunk_frames | seconds/chunk | segments | peak VRAM |
|---|---|---|---|
| 750 (baseline) | 30 | 1 | 9235 MiB |
| 375 | 15 | 2 | 5481 MiB |
| **250** | 10 | 3 | **4631 MiB** |
| 150 | 6 | 4 | 4631 MiB |

At chunk ≤ 250 the decode stage falls below the LM stage → peak plateaus at **4631 MiB = the LM stage**
(Q4 weights 2.86 + KV 1.47 + act). So chunking caps the decode stage at ANY song length; 250 is the
sweet spot (largest chunk that hits the plateau, best crossfade quality). Decode-stage VRAM is now
duration-independent. Remaining wall: the LM stage (KV-dominated) → Lever 3 (KV).

## Lever 2 — flash attention on the LM decode (DONE, validated)
Switched both decode attention paths (`sggen_attn`, `sggen_attn_batch`) from the manual
QKᵀ/softmax/transpose/×V chain to `ggml_flash_attn_ext` (SGLM_NO_FA reverts). The prefill oracle
(`songgen-lelm.h`) already used FA and passes the golden gate, so FA is numerically faithful here
(>0.999 logit cossim; the original gate already compared FA-prefill vs manual-decode).
- **LM step 51 → 35 ms (−32%)**; KV-vs-prefill gate still PASS >0.999.
- **GPU SM utilization median 97%** during decode → FA already removed the launch-latency overhead;
  the decode is throughput-bound, NOT launch-bound (so CUDA-graph capture would not help).
- FA also reads K/V straight from the cache layout (un-transposed V) → enables a quantized KV cache.

## Lever 3 — Q8_0 KV cache (DONE, validated; found+fixed a latent corruption bug)
`SG_KV_TYPE=q8_0|q4_0|f16` (default f16; deploy uses q8_0). FA reads the quantized cache directly.
- **q8_0 KV: −47% (1468 → 780 MB @30s)**, gate PASS >0.999. q4_0 KV → CUDA illegal access (task #7).
- **BUG FOUND (ear-caught, "horror-movie wash"):** the single/prefill attention path hardcoded F16
  strides (`ggml_type_size(GGML_TYPE_F16)`) for the KV-cache write/read. With a Q8_0 cache the
  conditioning-prefix KV was written at F16 offsets while the batched decoder read at Q8_0 offsets
  → corrupted prefix → degenerate generation. The KV-vs-prefill gate MISSED it because there write+read
  use the same (wrong) strides → self-consistent. FIX: use the cache tensor's own `nb[]`. Isolation that
  caught it: FA+F16 = healthy song (flux 0.58); FA+Q8_0 = wash (flux 0.33, rms 0.09 ½ amplitude); after
  fix FA+Q8_0 @30s = flux 0.705, rms 0.19, healthy. LESSON: the logit gate is necessary but not
  sufficient — added a `wav_metric.py flux/flatness` regression check and ear-confirmation on every
  generation-path change (metrics alone declared a broken build "a win" once — don't repeat).

## ncu floor analysis (LM decode, Q4 weights, N=2)
`ncu --section SpeedOfLight` over a steady-state decode window:
| kernel | SM% | DRAM% | role |
|---|---|---|---|
| **mul_mat_vec_q** (dominant) | ~75 | ~70 | Q4 weight matmuls (q/k/v/o proj, MLP, lm_head) |
| dequantize_block | 39 | 28 | dequant |
| flash_attn_ext_f16 | 11 | 56 | FA (cheap, mem-bound on KV reads) |
The decode is dominated by `mul_mat_vec_q` at **~70–75% of BOTH compute and memory roofline** — near
the practical floor for N=2 quantized decode (weight-load bound). FA is cheap. No launch-bound idle
(97% SM). Materially faster would require fewer/smaller weights (already Q4) or higher effective batch
(decode is fixed at N=2 for CFG). → LM decode is at its floor for this model+quant.

## FINAL deploy config + result
Weights are mmap'd (`gguf-weights.h` MAP_PRIVATE PROT_READ) → host RSS is file-backed/reclaimable, not anon.

**Shipping config (server defaults): Q4_K_M + flash-attn + Q8_0 KV + chunk_frames=200.**

| metric | baseline (Q8, unopt) | **shipped (Q4, opt)** |
|---|---|---|
| basic 30s peak VRAM | 9235 MiB | **3931 MiB** (−57%, under 4096) |
| basic 30s wall / RTF | 59.1s / 1.97 | **48.2s / 1.61** |
| LM step | 51 ms (Q4) | **35 ms** |
| KV @30s | 1468 MB | 780 MB (q8_0) |
| host RSS | 5.3 GB | 3.1 GB (mmap, reclaimable) |

- **Q8 cannot meet the 4 GB budget** at any settings — weights alone are 5.1 GB; leanest Q8
  (FA+Q8_0 KV+chunk) ≈ 6.2 GB @30s. Q5_K_M (~3.6 GB wts) + KV + act ≈ 4.7 GB also over. **Q4_K_M is the
  only quant that fits**, and the user judged it audibly OK. (Q8 stays as the quality option for non-budget hosts.)
- Decode-stage VRAM is now duration-independent (chunked); the LM stage (weights + KV) is the wall and
  scales with song length via KV: 3.93 GB @30s, ~4.2 GB @60s, ~4.5 GB @112s. To hold ≤4 GB at full song
  length needs q4_0 KV (task #7) or conditioning-prefix right-sizing — documented follow-ups.

## Open follow-ups (documented, deferred)
- **#7 q4_0 KV crash** — would ~halve KV again → ideal ~3.5 GB + long-song budget.
- **#6 clone/continue quality** — instrumental-only/garbled (prompt-audio conditioning path); ALSO the
  clone/continue ENCODE stage is an unchunked VRAM hog (MusicFM ×2 over a 40s tile → 7437 MiB peak,
  the clone wall), needs the same chunking treatment as the decode.
- **conditioning-prefix right-sizing** — the static ~952-token prefix dominates KV at short gens; trimming
  desc 600→actual-lyric-length would cut KV further (verify the padding isn't load-bearing first).
